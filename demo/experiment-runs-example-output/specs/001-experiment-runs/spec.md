# Feature Specification: Experiment Runs API (Single User, No Auth)

**Feature Branch**: `001-experiment-runs`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "Build a small Experiment Runs API that lets a single ML engineer log model training runs. A run has a name, a model type, a set of hyperparameters, and an optional time budget in minutes. The engineer can list their runs, finish a run by recording its final metrics, and delete a run. They need to see stalled runs, ones still running past their time budget, at a glance, and must never lose data on a crash. There is no authentication in this release: one user, one process."

## Clarifications

### Session 2026-10-10

- Q: In what order does the list endpoint return runs? → A: Stalled runs first (longest-running first), then other running runs (oldest first), then finished runs (most recently finished first).
- Q: What format are run identifiers? → A: UUID version 4 strings, generated by the server.
- Q: What is the minimum observability bar? → A: Structured JSON logs to stdout for every request outcome, every persistence write (success or failure, with the error class), and every startup and shutdown event. No metrics endpoint in this release.
- Q: What happens when the store file exists but is unreadable or corrupted at startup? → A: Refuse to start: rename the bad file to `<store>.corrupt.<UTC timestamp>`, log the rename, and exit non-zero. The next start sees no store and begins empty.
- Q: What happens when a run that is already finished is finished again? → A: Reject it with a conflict error and keep the original metrics. Recorded results are immutable.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Log and list runs (Priority: P1)

The engineer starts a training job and logs it as a run with a name, the model
type, and the hyperparameters used, optionally with a time budget. They can
list every run they have logged and see which are still running and which are
finished.

**Why this priority**: Without logging and listing runs the API has no value.
This is the smallest slice that is usable end to end.

**Independent Test**: Start the service with an empty store, log three runs
(one with a time budget, two without), list them, and check all three appear
with the right names, model types, hyperparameters, and status "running".

**Acceptance Scenarios**:

1. **Given** an empty store, **When** the engineer logs a run named "baseline" with model type "logistic_regression" and hyperparameters `{"learning_rate": 0.05, "epochs": 20}`, **Then** the run is stored and appears in later list calls with status "running" and the same hyperparameters.
2. **Given** an empty store, **When** the engineer logs a run with a time budget of 30 minutes, **Then** the run is stored with that budget and appears in the list.
3. **Given** two runs already logged, **When** the engineer lists runs, **Then** both are returned, each with a stable identifier.
4. **Given** the engineer submits a run whose name is empty or only whitespace, **When** the request is processed, **Then** it is rejected with a clear validation error and nothing is stored.

---

### User Story 2 - Never lose data across crashes (Priority: P1)

The engineer expects their run log to be there tomorrow, even if the process
crashes, the machine loses power, or the service is killed mid-write. After a
restart, every run that was acknowledged as logged, finished, or deleted
reflects that state, and no run is ever seen half-written.

**Why this priority**: The user stated it as non-negotiable ("must never lose
data on a crash"). A run log that silently loses results is worse than none,
because it hides which experiments were already tried.

**Independent Test**: Log N runs, kill the process abruptly (for example with
SIGKILL) at arbitrary points during writes, restart, list the runs, and check
the store is always consistent: each write is either fully applied or not
applied at all.

**Acceptance Scenarios**:

1. **Given** a run was logged and the response was returned, **When** the process restarts, **Then** the run appears in the next list with the same identifier and fields.
2. **Given** a write is interrupted before a success response is returned, **When** the process restarts, **Then** the store is readable and contains either the complete change or no trace of it.
3. **Given** a store file from an earlier run of the service, **When** the service starts, **Then** it loads every stored run without loss.

---

### User Story 3 - Finish and delete runs (Priority: P2)

When training ends, the engineer finishes the run by recording its final
metrics (for example validation AUC and loss). If a run was logged by mistake
or is no longer useful, they delete it.

**Why this priority**: Finishing runs is what makes the log useful for
comparing experiments, but a first demo could show logging and listing alone.

**Independent Test**: Log two runs, finish one with metrics, delete the other,
then list: the finished one shows status "finished" with its metrics, and the
deleted one is gone.

**Acceptance Scenarios**:

1. **Given** a running run, **When** the engineer finishes it with metrics `{"val_auc": 0.91}`, **Then** later lists show it as "finished" with those metrics and a finish time, and it survives a restart.
2. **Given** an existing run, **When** the engineer deletes it, **Then** it no longer appears in lists and does not come back after a restart.
3. **Given** an identifier that does not exist, **When** the engineer tries to finish or delete it, **Then** the request is rejected with a clear "not found" error and no other run changes.
4. **Given** a run that is already finished, **When** the engineer finishes it again, **Then** the request is rejected with a conflict error and the original metrics are kept.

---

### User Story 4 - See stalled runs at a glance (Priority: P2)

The engineer wants to spot runs that are stalled, still running past their
time budget, without scanning and comparing timestamps by hand. Stalled runs
usually mean a hung job, a crashed worker that never reported, or a budget set
too low.

**Why this priority**: Explicitly requested ("see stalled runs at a glance").
It builds on User Story 1 and is small and well scoped.

**Independent Test**: Log runs with a short budget, a long budget, and no
budget, let time pass beyond the short budget, list the runs, and check each
carries a correct stalled indicator.

**Acceptance Scenarios**:

1. **Given** a running run whose time budget has been exceeded, **When** the engineer lists runs, **Then** the run is flagged as stalled.
2. **Given** a running run still within its budget, **When** the engineer lists runs, **Then** it is not flagged as stalled.
3. **Given** a running run without a time budget, **When** the engineer lists runs, **Then** it is never flagged as stalled.
4. **Given** a finished run that took longer than its budget, **When** the engineer lists runs, **Then** it is not flagged as stalled.

---

### Edge Cases

- **Empty or whitespace name or model type**: rejected at creation with a validation error; nothing is stored. Leading and trailing whitespace is trimmed from accepted values.
- **Very long names**: names over 200 characters and model types over 100 characters are rejected.
- **Hyperparameters**: values must be strings, integers, floats, or booleans (nested objects and lists are rejected); at most 50 entries; keys must be 1 to 100 non-blank characters; `NaN` and infinite values are rejected.
- **Metrics**: at least one and at most 50 entries; every value must be a finite number; booleans are not numbers. The request body is validated before the identifier is looked up.
- **Time budget**: optional; when present it is a whole number of minutes from 1 to 10,080 (one week).
- **Client-supplied identifiers**: a create request containing an `id` (or any unknown field) is rejected.
- **Unknown identifiers**: finish and delete return "not found"; list is unaffected. A malformed identifier is treated the same as an unknown one.
- **Concurrent writes within the single process**: serialized, so two writes can never interleave and corrupt the store.
- **Store file missing at startup**: treated as an empty store; the first write creates it atomically.
- **Store file present but corrupted** (it can be read but not parsed): startup renames it to `<store>.corrupt.<UTC timestamp>`, logs the event, and exits non-zero so the operator can inspect or restore it. A quarantined file is never overwritten.
- **Store file present but unreadable** (no permission, or the path is a directory): startup logs the problem and exits non-zero without renaming or changing anything, because fixing access is enough to recover. A store path that is an existing directory is rejected as invalid configuration.
- **Clock and timezone**: all timestamps are UTC; "stalled" is evaluated against the server's current UTC time at read time, so it is independent of the server's local timezone.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow logging a run with a required name, a required model type, optional hyperparameters, and an optional time budget in minutes.
- **FR-002**: System MUST reject a run whose name or model type is missing, empty, or only whitespace, with a clear validation error, and store nothing.
- **FR-003**: System MUST give each run a stable, unique identifier that never changes. Identifiers MUST be UUID version 4 strings in canonical hyphenated form, generated by the server; client-supplied identifiers MUST be rejected.
- **FR-004**: System MUST allow listing all runs, returning for each its identifier, name, model type, hyperparameters, time budget (if any), status (running or finished), start time, finish time (if finished), metrics (if finished), and a stalled indicator.
- **FR-004a**: The list MUST be ordered: (1) stalled runs first, by start time ascending; (2) then the other running runs, by start time ascending; (3) then finished runs, by finish time descending. Ties are broken by identifier.
- **FR-005**: System MUST allow finishing a running run by its identifier, recording a set of named numeric metrics and the finish time.
- **FR-006**: Finishing a run that is already finished MUST be rejected with a conflict error and MUST NOT change its metrics or finish time.
- **FR-007**: System MUST allow deleting an existing run by its identifier.
- **FR-008**: Finish and delete requests that reference an unknown identifier MUST return a clear "not found" error and leave every other run unchanged.
- **FR-009**: A run MUST be flagged as stalled if and only if it is running, has a time budget, and the time since it started is strictly greater than the budget. "Now" MUST be the server's current UTC time, read once per list request.
- **FR-010**: System MUST persist every acknowledged create, finish, and delete so it survives a process restart.
- **FR-011**: System MUST make every persistent write atomic: after any crash the stored state is either the state before the write or the fully applied state after it, never partial or corrupted.
- **FR-012**: On startup, System MUST load every stored run and expose it through the list operation without loss.
- **FR-013**: If the store exists and can be read but cannot be parsed at startup, System MUST (a) rename the file to `<store-path>.corrupt.<UTC timestamp>` so its contents are kept and never overwritten, (b) emit a structured log line naming the failure and the new path, and (c) exit with a non-zero status without starting with an empty store on that launch. The next launch, finding no store, MUST start empty. If the store exists but cannot be read at all, System MUST log the failure and exit with a distinct non-zero status without renaming or modifying the file.
- **FR-014**: System MUST NOT require or perform authentication or authorization in this release; every caller is treated as the single owner of every run.
- **FR-015**: System MUST serialize concurrent write operations within the process so they cannot interleave and corrupt the stored state.
- **FR-016**: System MUST emit one structured JSON log line to stdout per request outcome, with at least: timestamp, operation (one name each for create, list, finish, and delete; `unknown` for requests that match no operation), outcome (success or the error class), and the run identifier when the request path contains one.
- **FR-017**: System MUST emit one structured JSON log line to stdout per persistence write attempt, with at least: timestamp, outcome (success or error class name), and, on failure, the error message.
- **FR-018**: System MUST emit one structured JSON log line to stdout once it is accepting requests (saying whether the store existed and how many runs were loaded), one at graceful shutdown (an interrupt or a termination signal), and one when it fails to start, giving the reason.
- **FR-019**: System MUST NOT expose a metrics endpoint, a health endpoint, or interactive API documentation in this release.

### Key Entities

- **Run**: one training run of one model.
  - Attributes: identifier (UUID v4, server-assigned), name, model type, hyperparameters (name to scalar value), time budget in minutes (optional), status (running or finished), started-at timestamp, finished-at timestamp (only when finished), metrics (name to finite number, only when finished).
  - Derived at read time: stalled indicator (running, has a budget, and over it).
- **Run Store**: the single persistent collection of every run for the one user of this release. It has exactly one on-disk representation, updated atomically.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An engineer can log their first run and see it in the list within one pair of requests (one create, one list), with no configuration beyond starting the service.
- **SC-002**: After any abrupt termination during normal use, a restart finds 100% of acknowledged runs intact and 0% partial or unreadable, verified by a crash-during-write test of at least 50 iterations without one corrupted store.
- **SC-003**: For a store of at least 100 runs mixing stalled, running, and finished entries, 100% of stalled runs carry `stalled: true`, 0% of other runs do, and every stalled run is listed before any other run, with no client-side filtering or sorting.
- **SC-004**: Every operation (create, list, finish, delete) completes in under 100 ms at the 95th percentile with 1,000 runs in the store on a typical developer laptop.
- **SC-005**: Finish or delete on an unknown identifier returns "not found" in 100% of cases and never changes any other run.
- **SC-006**: Zero runs are lost across 100 consecutive restart cycles under a workload mixing creates, finishes, and deletes.

## Assumptions

- **Single user, single process**: exactly one caller and one running instance at a time. Multi-process or multi-writer safety is out of scope.
- **No authentication in this release**: the service runs on a trusted local machine and, by default, accepts connections only from that machine. Adding authentication is future work.
- **Local file storage**: given the single-user, single-process scope, one local file replaced atomically on every change is the storage. No database.
- **Runs are logged, not executed**: the API records runs; it does not start, monitor, or stop training jobs. "Stalled" is advisory.
- **Metrics are final values only**: one value per metric name, recorded at finish. Per-epoch metric history is out of scope.
- **Reasonable limits**: names up to 200 characters and model types up to 100 (after trimming), at most 50 hyperparameters and 50 metrics, keys up to 100 characters, budgets up to one week.
- **No pagination in this release**: list returns every run. At single-user scale this is acceptable; pagination is a future enhancement.
